## Update Cluster Flow Overview
To maximize efficiency and minimize bandwidth cycles, we will pull all required dependencies inside a single configuration file at one time:
1. The target OpenShift Platform release images (v4.18.43).
2. The updated Operator index catalog including OpenShift GitOps for version 4.18.
3. Essential supplemental base images (ubi8-minimal).

## Part 1: Low-Side Preparation (On Jump Server 🟣)

<br>

### Step 1.1: Create the Working Directory
Create a dedicated workspace directory on the low-side storage partition to hold the configuration and downloaded mirror artifacts.

```bash
mkdir -p /mnt/low-side-data/upgrade-ocp
cd /mnt/low-side-data/upgrade-ocp
```

<br>

### Step 1.2: Generate the Unified ImageSetConfiguration
Create the `imageset-config.yaml` file to pull the platform components, operators, and baseline images concurrently.

```bash
cat << EOF > /mnt/low-side-data/upgrade-ocp/imageset-config.yaml
---
kind: ImageSetConfiguration
apiVersion: mirror.openshift.io/v2alpha1
mirror:
  platform:
    channels:
    - name: stable-4.18
      type: ocp
      minVersion: 4.18.43
      maxVersion: 4.18.43

  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.18
    packages:
    - name: openshift-gitops-operator
      channels:
      - name: latest

  additionalImages:
  - name: registry.redhat.io/ubi8/ubi-minimal:latest

  helm: {}
EOF
```

<br>

### Step 1.3: Execute the Mirror Process
Run the `oc-mirror` utility to fetch the remote dependencies and store them as a local file-based repository.

```bash
oc-mirror --config=imageset-config.yaml file:///mnt/low-side-data/upgrade-ocp/ --v2
```

# Part 2: Asset Transfer, Registry Ingestion, and Cluster Configuration

### Step 2.1: Transfer the Mirror Artifacts
Synchronize the entire working directory from the JUMP server to the HIGHSIDE storage subsystem over the internal network boundary using `rsync`.

```bash
rsync -avP /mnt/low-side-data/upgrade-ocp highside:/mnt/high-side-data/
```

### Step 2.2: Push Assets to the High-Side Registry  
VERIFY you are on **Highside Server** (🟠 Orange prompt) !  

Log into the HIGHSIDE server terminal. Navigate to the synchronized path and use the `oc-mirror` ingestion execution mode to populate your target localized enterprise registry.

```bash
ssh highside

cd /mnt/high-side-data/upgrade-ocp

# Note: Execute podman login if your local registry requires active authentication credentials
oc-mirror -c imageset-config.yaml --from=file:///mnt/high-side-data/upgrade-ocp/ docker://$(hostname):8443 --v2
```

<br><br>

### Step 2.3: Apply Cluster Mirror Configuration
When the ingestion process completes, `oc-mirror` outputs the generated deployment manifests inside the `working-dir/cluster-resources/` path.  
Apply the updated files. 
This includes the new ImageDigestMirrorSet (IDMS), CatalogSources, and cryptographic signature ConfigMaps needed for the 4.18 environment.

```bash
cd /mnt/high-side-data/upgrade-ocp/working-dir/
ll cluster-resources/

# Authenticate to the target cluster if your active session has expired
oc login https://api.disco.lab:6443 --username kubeadmin

# Apply all generated resources collectively
oc apply -f /mnt/high-side-data/upgrade-ocp/working-dir/cluster-resources/
```

<br>

### Step 2.4: Verify The state of Cluster - MachineConfigPool (MCP) Stabilization
Applying a new IDMS resource triggers a rolling configuration update across your master and worker nodes. You **must** wait until all pools are completely updated and settled before initiating any upgrade commands.

```bash
oc get mcp -w
```
> [!IMPORTANT]
> Do not proceed to the upgrade phase until all pools display `UPDATING=False` and `DEGRADED=False`.

## Part 3: Compiling the Release Target
Because this cluster operates in a fully disconnected environment, it cannot automatically determine upgrade pathways from the public internet. You must explicitly construct the target release image reference and command the Cluster Version Operator (CVO) to execute.

To form the explicit upgrade string, you need to collect two components:
1. The exact SHA256 release digest identifier.
2. The exact local internal registry image repository route.

### Step 3.1: Extract Release Metadata

First, find the signature file matching your target release to pull the target SHA256 hash string:

```bash
ls /mnt/high-side-data/upgrade-ocp/working-dir/signatures/
```

*Locate the segment directly following the `sha256-` prefix (e.g., `27eafee2d15ebe7d66cf14aeefbb79f91512669ecee1facf3ee5f06019dca651`). Save this value.*

<br><br>

Second, inspect your generated IDMS manifest to find your precise local repository path:
```bash
cat /mnt/high-side-data/upgrade-ocp/working-dir/cluster-resources/idms-oc-mirror.yaml
```
*Identify the mirror block entry mapping to `openshift/release-images` (e.g., `ip-XXYYXXYY.eu-central-1.compute.internal:8443/openshift/release-images`).*

<br>

Combine the internal registry path with the extracted digest identifier using the `@sha256:` convention format:
`[LOCAL_REGISTRY_PATH]@sha256:[EXTRACTED_DIGEST]`

**Target Example String:**
```text
ip-10-0-48-225.eu-central-1.compute.internal:8443/openshift/release-images@sha256:27eafee2d15ebe7d66cf14aeefbb79f91512669ecee1facf3ee5f06019dca651
```

<br>

### Step 3.2: Initiate the Explicit Upgrade Command
Execute the administrative platform upgrade command. The `--allow-explicit-upgrade` flag tells the CVO to proceed with your specified manifest image directly.

```bash
oc adm upgrade --to-image=ip-XXXXX.eu-central-1.compute.internal:8443/openshift/release-images@sha256:XXXXXXXXXXXXXXX --allow-explicit-upgrade
```

## Part 4: Upgrade Monitoring and Troubleshooting

The platform update process will sequentially cascade updates across core platform controllers and individual host operating systems (RHCOS).

### Step 4.1: Monitor the Overall Upgrade Progress
Track progress metrics, version state machine status, and current operations.

```bash
oc adm upgrade
```

Alternatively, watch the raw state values of the ClusterVersion definition:
```bash
oc get clusterversion -w
```

### Step 4.2: Audit Cluster Operator Stability
Operators will cycle through alternating availability and processing modes during container replacements. Watch to ensure all infrastructure processes return to a steady, fully updated condition.

```bash
oc get co
```

### Step 4.3: Final Verification
The upgrade process is verified complete once `oc adm upgrade` indicates that the cluster is stable on version 4.18.43 and all nodes reflect the updated underlying infrastructure engine.

```bash
oc get nodes
```
