# Lab 4.1: Upgrade Path Validation and Unified Asset Mirroring

This lab covers the initial phase of upgrading your disconnected OpenShift cluster from version 4.17.50 to 4.18.43. You will configure and execute a single, unified mirror operation on the internet-connected environment to pull the platform release, required operators, and additional base images.

## Prerequisites

Before executing the mirror process, ensure you have validated the direct upgrade path (4.17.50 -> 4.18.43) using the official Red Hat Upgrade Graph tool:
Red Hat Upgrade Graph: https://access.redhat.com/labs/ocpupgradegraph/update_path

---

## Part 1: Low-Side Preparation (JUMP Server)

All commands in this section must be executed exclusively on the JUMP server (the internet-connected terminal).

### Step 1.1: Create the Working Directory
Create a dedicated workspace directory on the low-side storage partition to hold the configuration and downloaded mirror artifacts.

```bash
mkdir -p /mnt/low-side-data/upgrade-ocp
cd /mnt/low-side-data/upgrade-ocp
```

### Step 1.2: Generate the Unified ImageSetConfiguration
Create the `imageset-config.yaml` file. This configuration uses the `v2alpha1` API to pull the specific OpenShift release, the updated GitOps operator catalog for 4.18, and the required UBI minimal image in a single execution.

```bash
cat << EOF > /mnt/low-side-data/upgrade-ocp/imageset-config.yaml
---
kind: ImageSetConfiguration
apiVersion: mirror.openshift.io/v2alpha1
mirror:
  platform:
    channels:
    - name: stable-4.18
      type: ocp
      minVersion: 4.18.43
      maxVersion: 4.18.43

  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.18
    packages:
    - name: openshift-gitops-operator
      channels:
      - name: latest

  additionalImages:
  - name: registry.redhat.io/ubi8/ubi-minimal:latest

  helm: {}
EOF
```

### Step 1.3: Execute the Mirror Process
Run the `oc-mirror` command to download all specified assets into a local file-based registry structure inside your working directory. Ensure your Red Hat pull secret is properly configured and accessible.

```bash
oc mirror --config=/mnt/low-side-data/upgrade-ocp/imageset-config.yaml file://mirror-output
```

---

## Next Steps
Once the mirror command completes successfully, all required assets will be stored locally within the `mirror-output` directory on the JUMP server. Proceed to the next lab to package and transfer these assets to the HIGHSIDE environment.

# Lab 4.2: Asset Transfer, Registry Ingestion, and Cluster Configuration

This lab covers transferring the mirrored assets from the JUMP server to the HIGHSIDE environment, pushing them to your local enterprise registry, and configuring the OpenShift cluster to map the new v4.18 image digests.

## Part 1: Asset Transfer and Registry Ingestion

### Step 2.1: Transfer the Mirror Artifacts
Physically transfer or copy the `mirror-output` directory generated in Lab 4.1 from the JUMP server to the HIGHSIDE server. Ensure the folder is placed in an accessible directory, for example: `/mnt/high-side-data/upgrade-ocp/`.

### Step 2.2: Push Assets to the High-Side Registry
On the HIGHSIDE server, execute the `oc-mirror` command to read from the local file structure and push all images (Platform, Operators, and Additional Images) into your internal enterprise registry.

```bash
oc mirror --from=file:///mnt/high-side-data/upgrade-ocp/mirror-output docker://registry.highside.local/ocp4
```
*Note: Replace `registry.highside.local/ocp4` with your exact internal registry endpoint and targeted repository path.*

---

## Part 2: Cluster Mirror Configuration

When `oc-mirror` completes the ingestion process, it automatically generates a subfolder named `oc-mirror-workspace/src/results-XXXXXX/` containing the required Kubernetes manifests.

### Step 2.3: Apply the New ImageDigestMirrorSet (IDMS)
Apply the generated IDMS configuration to the cluster. This tells the internal cluster nodes to redirect image pull requests for OpenShift 4.18 from official Red Hat registries to your local high-side registry.

```bash
cd /mnt/high-side-data/upgrade-ocp/mirror-output/oc-mirror-workspace/src/results-*
oc apply -f imagedigestmirrorset.yaml
```

### Step 2.4: Apply the Updated Operator CatalogSource
Apply the generated CatalogSource manifest to make the OpenShift GitOps operator catalog for version 4.18 available in the cluster marketplace.

```bash
oc apply -f catalogsource-cs-redhat-operator-index.yaml
```

### Step 2.5: Verify MachineConfigPool (MCP) Stabilization
Applying an IDMS triggers a rolling update across your nodes via the Machine Config Operator. You **must** wait until all pools (master and worker) are completely updated and show `DEGRADED=False` and `UPDATING=False` before initiating the upgrade.

```bash
oc get mcp -w
```
*Do not proceed to Lab 4.3 until all pools show UPDATING=False.*

# Lab 4.3: Executing and Monitoring the Disconnected Cluster Upgrade

This lab covers triggering the actual cluster platform upgrade from 4.17.50 to 4.18.43 within the air-gapped environment and monitoring the lifecycle of the cluster operators.

## Part 1: Upgrade Triggering

Because the cluster has no internet access to pull the official Red Hat upgrade graph, you must explicitly point the Cluster Version Operator (CVO) to the exact release image digest hosted on your internal registry.

### Step 3.1: Retrieve the Target Release Image Digest
Locate the generated `release-images` metadata file inside your results directory to extract the exact SHA256 digest for the 4.18.43 release image, or pull it directly from your registry mappings file. The string will look similar to this:
`registry.highside.local/ocp4/openshift/release-images@sha256:example123...`

### Step 3.2: Initiate the Explicit Upgrade Command
Run the upgrade command using the `--to-image` flag. The `--allow-explicit-upgrade` flag is mandatory because you are bypassing the default automated upgrade path manager.

```bash
oc adm upgrade --to-image=registry.highside.local/ocp4/openshift/release-images@sha256:<YOUR_TARGET_DIGEST_HERE> --allow-explicit-upgrade
```

---

## Part 2: Upgrade Monitoring and Troubleshooting

The upgrade process will update the Cluster Version Operator, followed by a rolling update of all core platform operators and node operating systems (RHCOS).

### Step 3.3: Monitor the Overall Upgrade Progress
Track the percentage of completion and the current action being performed by the CVO.

```bash
oc adm upgrade
```

Alternatively, watch the raw status fields of the ClusterVersion object:

```bash
oc get clusterversion -w
```

### Step 3.4: Audit Cluster Operator Stability
During the upgrade, various operators will temporarily show `PROGRESSING=True` and `AVAILABLE=False`. Monitor the operators to ensure they resolve back to a healthy state.

```bash
oc get co
```

### Step 3.5: Final Verification
The upgrade is successfully completed when the `oc adm upgrade` command outputs that the cluster is stable on version 4.18.43 and all cluster nodes report the new Kubernetes version.

```bash
oc get nodes
```
