# Lab 4.1: Upgrade Path Validation and Unified Asset Mirroring

This lab covers the initial phase of upgrading your disconnected OpenShift cluster from version 4.17.50 to 4.18.43. You will configure and execute a single, unified mirror operation on the internet-connected environment to pull the platform release, required operators, and additional base images.

## Prerequisites

Before executing the mirror process, ensure you have validated the direct upgrade path (4.17.50 -> 4.18.43) using the official Red Hat Upgrade Graph tool:
Red Hat Upgrade Graph: https://access.redhat.com/labs/ocpupgradegraph/update_path

---

## Part 1: Low-Side Preparation (JUMP Server)

All commands in this section must be executed exclusively on the JUMP server (the internet-connected terminal).


## Update cluster Flow

After we check our flow version upgrade in: https://access.redhat.com/labs/ocpupgradegraph/update_path
you need to Dwonload our new version
- for fast time in ImageSet.yaml configuration we are bring the:
  - New Openshift Version
  - New Operator Index + Openshift gitops for 4.18
  - our New Image (ubi8)

  ALL IN 1 YAML TIME



### Step 1.1: Create the Working Directory
Create a dedicated workspace directory on the low-side storage partition to hold the configuration and downloaded mirror artifacts.

```bash
mkdir -p /mnt/low-side-data/upgrade-ocp
cd /mnt/low-side-data/upgrade-ocp
```

### Step 1.2: Generate the Unified ImageSetConfiguration
Create the `imageset-config.yaml` file. This configuration uses the `v2alpha1` API to pull the specific OpenShift release, the updated GitOps operator catalog for 4.18, and the required UBI minimal image in a single execution.

```bash
cat << EOF > /mnt/low-side-data/upgrade-ocp/imageset-config.yaml
---
kind: ImageSetConfiguration
apiVersion: mirror.openshift.io/v2alpha1
mirror:
  platform:
    channels:
    - name: stable-4.18
      type: ocp
      minVersion: 4.18.43
      maxVersion: 4.18.43

  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.18
    packages:
    - name: openshift-gitops-operator
      channels:
      - name: latest

  additionalImages:
  - name: registry.redhat.io/ubi8/ubi-minimal:latest

  helm: {}
EOF
```



### Step 1.3: Execute the Mirror Process
Run the `oc-mirror` command to download all specified assets into a local file-based registry structure inside your working directory. Ensure your Red Hat pull secret is properly configured and accessible.

```bash
oc-mirror --config=imageset-config.yaml file:///mnt/low-side-data/upgrade-ocp/ --v2
```

# Lab 4.2: Asset Transfer, Registry Ingestion, and Cluster Configuration

This lab covers transferring the mirrored assets from the JUMP server to the HIGHSIDE environment, pushing them to your local enterprise registry, and configuring the OpenShift cluster to map the new v4.18 image digests.

## Part 1: Asset Transfer and Registry Ingestion

### Step 2.1: Transfer the Mirror Artifacts
Physically transfer or copy the `mirror-output` directory generated in Lab 4.1 from the JUMP server to the HIGHSIDE server. Ensure the folder is placed in an accessible directory, for example: `/mnt/high-side-data/upgrade-ocp/`.

```bash

rsync -avP //mnt/low-side-data/upgrade-ocp highside:/mnt/high-side-data/

```


### Step 2.2: Push Assets to the High-Side Registry
Log into the HIGHSIDE server terminal. Execute the `oc-mirror` command to read the transferred data from the local directory and push all platform images, operator catalogs, and additional images into your internal enterprise registry.

```bash
ssh highside

cd /mnt/high-side-data/upgrade-ocp
oc-mirror --from=file:///mnt/high-side-data/upgrade-ocp/ docker://$(hostname):8443 --v2
```

## Part 2: Cluster Mirror Configuration

When the ingestion process completes, `oc-mirror` generates the required Kubernetes manifests inside a dynamically named results directory within your local workspace.

### Step 2.3: Apply the New ImageDigestMirrorSet (IDMS)
Navigate to the generated results directory and apply the IDMS configuration. This directs the cluster nodes to pull the OpenShift 4.18 images from your local high-side registry instead of the external Red Hat registries.

```bash
cd /mnt/high-side-data/upgrade-ocp/oc-mirror-workspace/src/results-*
oc apply -f imagedigestmirrorset.yaml
```

### Step 2.4: Apply the Updated Operator CatalogSource
Apply the updated CatalogSource manifest to make the version 4.18 Red Hat operator index available in the cluster marketplace, enabling the update of the OpenShift GitOps operator.

```bash
oc apply -f catalogsource-cs-redhat-operator-index.yaml
```

### Step 2.5: Verify MachineConfigPool (MCP) Stabilization
Applying a new IDMS triggers a rolling configuration update across your cluster nodes via the Machine Config Operator. You must wait until all pools (master and worker) are completely updated and show `DEGRADED=False` and `UPDATING=False` before starting the platform upgrade.

```bash
oc get mcp -w
```
*Do not proceed to Lab 4.3 until all pools show UPDATING=False.*

# Lab 4.3: Executing and Monitoring the Disconnected Cluster Upgrade

This lab covers triggering the platform upgrade from 4.17.50 to 4.18.43 within the air-gapped environment and monitoring the platform operators as they transition.

## Part 1: Upgrade Triggering

Because the cluster is fully disconnected, you must manually extract the exact release image digest and provide it explicitly to the Cluster Version Operator (CVO).

### Step 3.1: Retrieve the Target Release Image Digest
Examine the generated release synchronization metadata or your registry mapping files to find the exact SHA256 digest for the 4.18.43 release image. The target string will follow this format:
`registry.highside.local/ocp4/openshift/release-images@sha256:<TARGET_SHA>`

### Step 3.2: Initiate the Explicit Upgrade Command
Execute the administrative upgrade command using the `--to-image` flag. The `--allow-explicit-upgrade` flag is required to bypass the default external graph validation.

```bash
oc adm upgrade --to-image=registry.highside.local/ocp4/openshift/release-images@sha256:<YOUR_TARGET_DIGEST_HERE> --allow-explicit-upgrade
```

---

## Part 2: Upgrade Monitoring and Troubleshooting

The upgrade process will sequentially update the CVO, core platform operators, and individual node operating systems (RHCOS).

### Step 3.3: Monitor the Overall Upgrade Progress
Track the progress percentage and current cluster upgrade operations.

```bash
oc adm upgrade
```

Alternatively, monitor the real-time status of the ClusterVersion resource:

```bash
oc get clusterversion -w
```

### Step 3.4: Audit Cluster Operator Stability
During the upgrade process, operators will temporarily cycle through `PROGRESSING=True` and `AVAILABLE=False` states. Monitor them to ensure they stabilize.

```bash
oc get co
```

### Step 3.5: Final Verification
The upgrade is complete when `oc adm upgrade` indicates that the cluster status is stable on version 4.18.43 and all nodes report the updated Kubernetes version.

```bash
oc get nodes
```
